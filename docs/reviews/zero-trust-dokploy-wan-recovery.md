これは隔離試験の設計と暫定値であり、実機の採寸・採用決定・実装済みの宣言ではない。外部の通信を止める試験は、既存ネットワークやPoCでは行わない。

## 断の境界と継続範囲

```text
【サイト内: WAN正常・断の両方で継続】
ローカルファイル／設備ソース → Landing → Raw／Bronze ──┐
オンプレSQL Server CDC → サイトKafka → ローカルconsumer ┘
    → Silver → Gold → ローカルの分析・監視・運用
    SeaweedFS: Icebergデータ／metadata、Lakekeeper: catalog／snapshot参照
    DuckDB／PyIceberg: サイト内処理・参照、Prometheus: ローカル監視
    設備時系列: ローカルInfluxDB（本案件の受入に必須）、ログ・バックアップ: サイト内保管

【外部経路: 独立して劣化・復旧】
承認済みGoldの確定snapshot → 永続配送待ち → 外部宛先（WAN復旧後に再送）
人の標準入口 → IdP／Access → Tunnel → 選択したUI
WAN断中のローカル業務 → 承認済みネットワーク＋ローカル認証 → 選択したUI
緊急復旧 → 限定・時間制約・監査付きの管理経路（SSH） → 復旧対象
```

- **サイト内経路。** 到達可能なローカルファイルや設備、同一サイトのSQL ServerとKafkaは処理を継続する。未到達の遠隔ソースは停止区間を別表示し、未受信分まで処理したとはしない。受入時にRaw／Bronze、Silver、Gold、SeaweedFSオブジェクト、LakekeeperカタログとIceberg snapshotを照合する。DuckDB／PyIcebergによるローカルな参照と、Prometheusのscrape・警報、本案件で必須のローカルInfluxDB書込み・クエリ、ログ保管／バックアップ検証もWANなしで実施する。
- **外部経路。** 外部DNS、外部IdP／Access、Tunnel、R2等はcoreのliveness／readinessの依存ではない。外部Goldの格納・公開に失敗してもcore取込、ローカルGold確定、監視とローカル利用を止めない。外部配送と人アクセスは別々に `cloud-degraded` を出す。標準の外部人経路は迂回させず、承認された利用者だけがローカル業務経路を使う。管理者のSSH break-glassを業務ログインに転用しない。
- **準備と再起動。** 稼働中の継続と、WAN断中のコールド再起動は別の試験。後者は事前配置したイメージ・設定、ローカルDNS／時刻／証明書と必要資源を使い、外部からpull・install・認証更新できない前提で確認する。初回構築や外部資格の更新は同じ保証に含めない。

現物の根拠は[core宣言](../../compose.yaml)、[外付けCDC](../../compose.cdc.yaml)、[CDC／再処理](../../native/cdc_shadow.py)、[ツール側InfluxDB](../../compose.tools.yaml)、[Prometheus](../../native/monitoring/prometheus.yml)、[バックアップ](../../scripts/backup-native.py)、[edge宣言](../../compose.cloudflare.yaml)。既存CDC Composeは外部に用意するKafka等を使用し、SQL ServerやサイトKafkaを自動で作らない。汎用のcore-localは用途に応じて構成を選べるが、本案件のcore-localはローカルInfluxDBを明示的に含める。WAN断中の設備時系列書込み・ローカルクエリの両方を証明できない構成は受入不可。既存Toolsセットから独立して選べるかは、秘密名・依存・既存データを保持して後続PRで確認する。ログは少なくともローカルDockerログを基準とし、ローカルの集約が選択された場合はその保存と再起動も試験する。これらの宣言だけではWAN継続を証明しない。

## 永続位置・順序・再送契約

| 境界 | 保存する位置／正本 | 復旧時の証明 |
| --- | --- | --- |
| ファイル → Raw／Bronze | ソース単位の不変ID、内容hash・ソース位置、受入結果、Raw位置、格納台帳。確定済み内容hashは保持する。 | 同一ID＋同一hashは重複適用0、同一ID＋異なるhashは競合を隔離。元ファイルと台帳の有効な位置から再開する。 |
| SQL Server → Kafka → consumer | ソースが提供するCDC位置（LSN等）、connectorの位置、topic・partitionごとのKafka offset、consumerの永続checkpoint。 | 位置の正本と更新責任を区別する。Rawの確定と対象位置の記録後にconsumer確定を進め、失敗前後で再開点を照合する。保持越えは区間／開始位置を記録し、無条件のoffsetリセットをしない。 |
| Raw → Silver／Gold | Rawの世代・入力位置とIcebergのtable/snapshot ID、入力の照合hash、カタログで確定を参照できるか。 | テーブルごとに選んだsnapshotで再現、ID集合と内容hashを比較する。partition内と業務キーに必要な順序だけ保証し、全partitionの総順序を仮定しない。 |
| Gold snapshot → 外部 | 世代・snapshot＋content hashから作る配送ID、試行状態、送信先確定、ローカルACKを別々に永続化。 | 相手確定後・ACK前の停止で同一バイトを確認して再送、既達と異内容を区別。全公開単位が確定してからmanifestを可視化する。欠損・重複適用は別々に判定。 |

設計上は障害時の少なくとも1回の再試行と冪等化を組み合わせ、跨るシステムの一括exactly-onceを約束しない。単一回復処理内で順序が必要な系列は先行世代を越して確定しない。スキーマ違反・hash不一致・反復失敗は理由付きquarantineへ隔離し、件数・保留開始・判断権限を追跡する。飛ばした対象を配送済みにしない。再送できない区間は資産・partition／世代・起点を記録して欠損として扱い、暗黙削除・大量再取込では回復しない。現行[R2 CLI](../../native/edge/r2.py)の内容照合付きcreate-onlyとmanifest最後の作り方は再利用候補であり、永続キュー・自動再送は後続PRの実装と検証が必要。

## 容量の暫定モデル

ピーク、イベントの平均／最大バイトと圧縮後の比率、同時並行、brokerのレプリカと実保持、既存PoCのピーク使用量、VMの実空きは要計測。たとえば次のようにプールごとに算出する。

- Kafkaプール = ピークイベント数/秒 × 1イベント当たりバイト × そのプールの保存率 × レプリカ数 × 有効保持秒 × 安全係数。オンプレ消費が継続しても再処理の必要期間を評価し、各brokerの偏り・segment・保持削除の遅れとディスク空きに余裕を取る。
- SeaweedFS／Icebergプール = Raw／Bronze／Silver／Goldの**独立に格納される増分**とデータ・metadata・snapshot保持、オブジェクト側の冗長化、更新時の書出し／compactionの一時容量。Icebergファイルを格納するSeaweedFSとIcebergの別名で同じバイトを加算しない。catalog DB自体のデータ／WALは別プール。
- 外部配送プール = 承認済みGoldの実効バイト/秒 × 断時間 × 安全係数 ＋ 実測の台帳・一時格納分。snapshot参照だけならデータを二重計上せず、その参照先の保持を固定する。別spoolへ複写する構成なら実バイトを追加する。
- 設備時系列、Prometheus、ログ、バックアップは各保持量と上限を分ける。バックアップはフル＋差分と世代、作成・検証の一時領域を計上し、独立保管先と復元試験を別途確認する。論理プールの合計でも、同一物理ディスクに載る分は既存PoC予約・空きの下限・一時容量を差し引いた共通枠で再判定する。

**合成例に限る。** 72時間断・24時間以内追いつきを仮置き。Kafka入力は100イベント/秒 × 1 KiB、保存率60%、レプリカ3、保持を再処理試験用96時間、安全係数1.30とすると約77.1 GiB。別のローカルオブジェクト増分70 KiB/秒（格納時圧縮後、冗長化1の合成条件）× 72時間 × 1.30 ≈ 22.5 GiB。Gold外部配送を50 KiB/秒と仮定し別spoolへ複写する場合、50 KiB/秒 × 72時間 × 1.30 ≈ 16.1 GiB。いずれも既存占有、catalog・監視／ログ／バックアップ・一時容量を含まないため、VM推奨サイズとして合計して使わない。72/24は上記を仮定した試験目標であり、実機の保証値ではない。レプリカ3も例で、単一brokerなどの実構成から耐障害性を推定しない。

| 未算定のプール（暫定的な算定・保全ルール） | 実測または合意待ち |
| --- | --- |
| Lakekeeper／catalog DB | DB増分・WAL・一時領域をオブジェクトプールと別に予約。増分、WALピーク、保持日数は未計測。 |
| InfluxDB・Prometheus | それぞれ格納後の増分 × 必要保持期間＋書込み・圧縮一時領域。設備点数、サンプル周期、系列数、保持は未確定。 |
| ローカルログ | 平常・障害時の格納後バイト/秒 × 保持秒、rotation上限と障害時の増大分を見込む。実測量・保持日数・集約先は未確定。 |
| ローカルバックアップ | フル容量 × 保持世代 ＋ 差分保管量 ＋ 作成・復元の最大一時容量。格納先はcore領域と分離する候補。実測サイズ、世代数、保存先・復元目標は未確定。 |

復旧中も新規承認対象が毎秒 `λ` 流入するなら、追いつき時間は `backlog / (持続可能な処理率 - λ)`。分母が0以下ならETAは未定（計測不能または追いつかない）として表示する。例では `50 × (72/24 + 1) = 200 KiB/s` が平均前提の最低持続量、30%余裕なら260 KiB/s相当の検証枠。測るのはアプリ確認済みバイト/秒であり、WANの物理リンク速度ではない。

## 監視、閾値、復旧操作

- ダッシュボードは未送達件数／バイト・最古の作成からの経過・承認済み世代、追いつきETAと計測窓、last success、retry／quarantine／重複抑止・gap、consumer lag／保持までの残時間、物理空きと各論理プールを表示する。ログにはrun ID／範囲／理由コードのみを残し、payloadや資格情報を含めない。
- 合成試験のフラグ例（**提案名であり設定未実装**）: `--warn-percent 70`、`--critical-percent 85`、`--stop-percent 95`、`--min-free-gib`。利用率は該当プールの予約容量に対して、空き閾値は共有物理容量に対して測る。警告で残時間・割当を確認、重大で新規の外部公開を抑制し担当へ通知、停止で当該spoolへの新規予約を止め、再取り出しできる確定snapshotと未受理範囲を保全。保全に必要な保持自体を確保できない場合は外部送信の欠損リスクを明示し、保持済みと表示しない。閾値・ヒステリシスは負荷実測で見直す。
- 外部配送quota満杯だけではオンプレの許可済み取込を停止しない。独立quota／予約によって優先すべきcore領域を確保する。物理ディスク全体の残量がcoreの保全下限を切る場合は別のインシデントとして、予約のない書込みを制限し、既存durable位置まで処理、sourceへ明示的backpressureまたは受入拒否、アラートを行う。受入不能・保持切れ・復旧不能の根拠を記録し、未確定を成功にしない。送信待ちの自動削除や既存PoCの一括削除はしない。
- 復旧はWAN、CPU、I/Oそれぞれに使ってよい上限を決める。提案する調整項目は送信バイト/秒、同時送信数、batchの上限・間隔、retry上限・backoff、共有I/O待ち、CPU使用率、core処理遅延、保持余力。低負荷で開始し、coreの受入／クエリ／監視が基準を外れた場合は配送を絞るか停止。計測する閾値は負荷とホスト資源により別途決める。
- **重大／停止時の運用手順。** 当番運用者に通知し、外部配送だけを一時停止または新規spool予約を保留する。確定snapshot、未予約範囲、優先度と永続位置を台帳で保全し、coreと既存PoCへの影響を確認する。容量または流量上限の変更は基盤・データ責任者の承認後、空きと下限を再計測して行う。確認済みcheckpointから制限付きで再開し、送信先とローカルのID／hash、欠損区間とquarantineを照合してからアラートを閉じる。担当者名・閾値の採用は作業票で管理する。
- 受入は断前／断中／復旧を同一runで連結する。人の外部認証だけ不通、外部Goldだけ不通、物理空き逼迫、断中の再起動、相手確定直後かつローカルACK前の停止、保持を跨ぐgapを別シナリオにする。全台帳・ID集合・内容hashと表示・アラートを照合し、cloud復旧とローカル継続は別判定とする。[試験表](zero-trust-dokploy-threat-test.md)に記録する。

実機の調査に反映する値は、VM空きと既存PoCのピーク、圧縮率、Kafkaレプリカ・partitionの偏り、各データストアの増分と一時容量、WAN転送実効値、承認する保持／復旧目標。隔離環境での受入以前に、障害条件とロールバック、既存データを保護する担当を決める。
