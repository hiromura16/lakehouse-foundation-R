本書は設計上の合格条件です。試験の実施結果ではありません。合成SQL Serverと隔離した一組のBroker、Connect、Coreを使用します。

各PRを最新mainから分離し、実装は既定OFF。必要な受入チェック、独立差分レビュー、公開内容の安全確認に合格してからマージし、マージ後の差分とCIを照合します。別工程での権限変更を同じPRに混ぜません。開発ブランチ・mainが配備トリガーにならないことは配備側で事前確認し、自動配備を機能検証に使いません。承認対象・版・SQL権限・ネットワーク・実行時間帯・保管先が不明ならサイト試験を保留します。

## 連結試験の最低証拠

一つの新規隔離環境で、合成データをSQLへ投入し、実Debeziumがsnapshotとstreamを流し、実KafkaからNative CDCが読むところまで時間を対応付けます。Raw記録、Silverのキー別結果、非空のGoldと期待する合計、確認済み確定位置が同じ試験に属することを照合します。同じ試験IDで稼働中のKafka Brokerが4.3.2、Connect workerの実ランタイムが台帳の承認版、ロードされたSQL Server Connectorが3.7.1.Finalであることを起動証跡または管理APIの限定情報から照合します。Broker、Connect・プラグインの版は別々に記録し、レジストリのタグだけでは証明しません。snapshot・stream、個別再起動、offset・履歴、既存volumeを保つrollbackと再開後の結果を同じ隔離連結環境で追跡します。合成KafkaイベントやSQL抽出の個別成功で代替しません。

| 変化 | 確認する内容 |
| --- | --- |
| 基本順序 | snapshotと追加・更新・削除後の期待行数・型・値を照合。NULLと空文字、符号付きdecimal、Unicode、bit、datetime2、許可したDDLを含める。 |
| 構成要素別の再起動 | Broker、Connect、Coreを一度にまとめてではなく、各々単独で停止・再起動。保持期間内に復帰し、直前の確定位置と履歴を維持して後続処理を続ける。確認済みACK、行と集計の一致、重複の抑制を照合。 |
| 保存失敗と正確な再開 | Rawを書き込む保存先を試験上だけ失敗させ、失敗対象のSQLite確定状態とKafkaのpartition別commit位置がどちらも直前から進まないことを確認する。障害を解除したら同じ位置から再処理し、対象のRaw・Silver・Goldと確定位置が期待値に一度だけ到達することを照合。 |
| 不正JSONと型付き隔離 | 不正JSONの受信原本はローカルに保全し、ACKせず後続位置も追い越さない。明示承認した型付き異常は契約に従い隔離し、正常確定と区別する。ローカル隔離/DLQ（処理不能イベントの隔離先）の件数、理由別件数と確定位置を比較し、本文は監視や公開ログに出さない。 |
| 遮断 | WANと外部DNS/レジストリを遮断し、事前ロード済みの同一成果物で停止状態から起動する。新規pullなしを通信証跡と同時に確認し、SQLからGoldまで進める。外部配送成功は求めない。 |
| 履歴・保持の異常 | 承認済みのpartition、cleanup、時間とbytes保持が一致し、再起動時に既存履歴を読み戻せることを確認。履歴の欠落・読取不可、設定差、topic再作成、最古LSNまたはBroker保持の境界超過なら準備完了と表示せず、新規登録や自動offset移動をしない。 |
| 実容量超過 | ホストの共有ディスクではなく、隔離した小さい専用領域の容量を使い切って実際の書込不能を発生させる。対象のSQLite/Kafka確定位置を進めず、履歴・Raw・checkpointを保全。容量を回復させて同じ入力位置から再開し、期待結果が一度だけ確定することを確認。保持の自動短縮、purge、上限の無断変更は禁止。 |

## 成果物の復元と上流の変更は別試験

1. 取得元の完全タグ、multi-platform index digest、採用プラットフォームのmanifest digest、config IDと、保管アーカイブのSHA-256を台帳で区別します。起動したConnectの版、署名または検証可能な由来、全同梱物のSBOM・ライセンス・CVE検査、実行試験結果を関連付けます。
2. 採用したOCI（イメージの標準形式）は管理レジストリまたはVM外保管を復元正本にします。空の別ストアを用意し、承認済みmanifestとすべてのblobを検証し、ロード後IDが一致することを確認します。同一ストア内のキャッシュ命中やタグの文字列一致だけでは合格にしません。
3. 空ストア復元と、既ロードの同一成果物で行うWAN断コールド起動を別試験にします。既存volumeを維持するrollbackも別に行い、履歴や状態の来歴と互換性を照合します。SQL・Kafka・Coreの復元順と到達位置を記録します。
4. 上流タグが動く事象は `UPSTREAM_CHANGED` として記録し、配備の参照先を自動で付け替えない。保管実体が欠損・相違なら復元失敗とし、上流のタグへ暗黙にフォールバックしません。採用更新は改めて同じゲートを通します。

## 容量とローカル観測

初期見積りはKafka 2vCPU/2–4GiB、Connect 1–2vCPU/2–4GiB、初期化時の上乗せ最大0.5vCPU/0.5GiB。いずれも実測前です。72時間のデータ領域は、イベント毎秒×保存bytes×259,200秒×複製係数に余裕を加え、利用上限で割ります。100件/秒、2KiB、RF1、30%の余裕、使用上限70%ならデータだけ約92GiBです。このデータ枠とは別に、空き作業領域、キャッシュ、各サービスのログ、アーカイブ、復元・展開・ローテーションの一時領域と同時ピークを個別に実測します。内部topic、index/segment、コンパクション作業領域、SQLログ、Coreも別枠です。復元時に同時に残る旧・新成果物や、一時ファイルシステムの空きも検査し、全領域を同一の空き容量として二重計上しません。partitionごとのretention.bytesと時間制限は早く到達する側が支配し、segment境界も試します。

Prometheus/Grafanaはローカル観測とし、Broker/Connect、task、履歴・内部topic、SQL最古/最新LSNとDebezium進捗、poll成功時刻、partition別end・commit・Raw確定、最古未処理、ローカル隔離/DLQの件数、ディスクと残保持時間を区別します。取得不能なら未確認。容量70%で警告、85%で重大、95%で運用担当が負荷停止を判断する暫定値を使い、自動purgeはしません。SQL CDC cleanupとKafka保持は別監視にし、必要位置の消失が迫れば入力を止めて保全します。

## DBAとサイト責任者への引き継ぎ

| 確認する人 | 引き継ぐ条件 |
| --- | --- |
| DBA | SQL Serverの版/Edition、Agent・CDCの状態、DBと専用オブジェクトの正当な所有、捕捉列・限定reader/writerと否定試験の承認を確認。capture/cleanup・保持LSN・ログ/ロックの負荷基準、既存系への影響、必要時の承認済み復旧手順を用意する。初回CDC有効化等は別手続きとする。 |
| サイト責任者 | Dokploy実版とApp/ネットワーク所有、SQLへの最小経路、CAと秘密保管、計測済みの各領域空き、成果物正本と別ストア復元証拠、ローカル監視、合意済み試験枠・停止/復帰条件を確認。PR/mainが自動配備につながらないことを配備前に確かめる。 |

この文書PRでは、実サイトの版、負荷、設定値、保存先、作業枠はいずれも未確認です。実接続、SQL/ジョブ/権限変更、データ読み取り、配備、サイト受入は行いません。実行可否は各担当が承認済み環境で判定し、不明項目が残る限りサイト受入を保留します。
